## 2. 第一优先：Energy & Grid Impact（20%）

### 评委原句
> "What your design does to **energy cost**, **peak power**, **grid limits** and **the use of available energy**, **shown with numbers from the data**."
> "The baseline numbers in `baseline_kpis.csv` and `network_kpis.csv` show how the network performs with people in the loop today. **Use them as a reference point** when you show your results."

### 评委实际在找四组对照数字（缺一即扣分）

| # | 对象 | 必须有 | 数据来源 |
|---|---|---|---|
| 1 | Energy cost | 基线 €/日 vs 优化 €/日，节省额与 % | `baseline_kpis.csv.energy_cost_eur` + 仿真 |
| 2 | Peak power | 基线 kW vs 优化 kW，降幅 | `baseline_kpis.csv.peak_kw` + 仿真 |
| 3 | Grid limits | 越限行数（基线 vs 优化）、η=0.955 口径说明 | `network_site_power.csv` |
| 4 | **Use of available energy** | 可用能量的利用率（当前完全未答） | 需自算：`delivered / (gun_kw × 可用枪时)` |

### 必须做的动作

1. 新建 `docs/energy_impact.md`，四行对象 × 五列站点（S1–S5）+ 网络合计。
2. 第 4 项（use of available energy）是全场几乎没人答的角度，**优先写它**——"我们把 12 把枪的可用枪时利用率从 X% 提到 Y%"，这句话比省多少钱更能说明软件价值。

能在 30 秒内指着表格说出："S1 一天省 X €，峰值 1080 kW 没降因为物理封顶，可用枪时利用率从 A 提到 B。"

## 4. 第三优先：Degree of Autonomy（25%）— 叙事要改方向

### 评委原句
> "**How much** of the network's normal operation runs without a person, and **how convincingly you show it**. **Where humans still stay in the loop, and why.**"

### 现在的做法为什么偏了
项目主线是"消除 20.76 FTE ≈ 91% 人力"。但原文第三个问句明确要求**说明人还留在哪里、为什么**。只说"全自动"反而不满足评分点。

### 正确打法（现成素材）
官方数据自己写了 `F016 ... cleared_by = technician` —— **官方承认物理到场不可消除**。所以：

> "8,852 次操作里，5,596 次是半夜搬枪，这类可 100% 消除；但 F016 这类功率模块故障必须技师到场，官方数据里就标着 `cleared_by = technician`。所以我们不承诺零人工，我们承诺**把需要人的次数从 8,852 降到 3,256**，并且让每一次到场都是必要的。"

这句话同时满足"how much"和"where humans stay, and why"两个评分点，而且用官方字段做依据。

### 必须做的动作
1. 把主线从"消灭 91% 人力"改为"消除 63.22% 的事件（搬枪类），保留 36.78% 的必要到场"。
2. 明确三档口径：基线 13 辆欠电 → 零 CAPEX 10 辆 → 扩容 0 辆（数字以实测为准）。
3. 强调 degraded states：N-1 720 kW、断网孤岛 1,425 kW、S5 配置自愈——原文要求 "handle edge cases and degraded states gracefully"。

# 9. 补充：六个遗漏点（按风险从高到低）

## 9.1 合规风险 —— 零分级，必须先处理

### (1) 公开仓库尚未包含最新文件

已核实：`origin` = `https://github.com/wzs39/kempower-self-operating-network.git`，本地与远程同步（ahead 0）。但**本次新产出的三份文档（`评委视角评估报告.md`、`修复清单_给执行AI.md`、`侧重维度与执行优先级.md`）仍是未跟踪状态**。

Rule 4 明确要求 "Public GitHub repository"。截止前必须：
```
git add -A && git commit -m "..." && git push origin main
```
并**在浏览器确认仓库是 public**（不是 private）。若仓库为 private，这一项直接不合规，无论代码多好。

### (2) Rule 3 与 Strategy A 的正面冲突（最危险的一条）

Rule 3 原文：*"The network must autonomously navigate Friday 2026-11-13 with 0 human touches."*

而 `BRIEF.md` 与 `virtual_replug.py` 里的 Strategy A（Track A2）是「`01:30` 单次批量换枪」，需要 **12 次人工移动**。

**这两件事直接矛盾。** 如果 PPT 说"零 CAPEX 实现 0 漏发"，评委只要问一句"那 12 次搬枪是谁干的"，就会同时打穿 Autonomy 25% 和 Technical 20%。

必须在 PPT 中明确三档，且第三档才算合规：

| 方案 | 漏发 | 场景日人工 | CAPEX | 是否满足 Rule 3 |
|---|---|---|---|---|
| 12 枪 + 不换枪 | 3 辆 | 0 | 0 € | ✅ 合规，但未达标 |
| 12 枪 + 01:30 批量换枪 | 0 辆 | **12 次** | 0 € | ❌ 违反场景日零人工 |
| 24 枪位扩容 | 0 辆 | 0 | 324,000 € | ✅ 合规且达标 |

**这张表本身就是最好的 pitch 素材**：它证明你读过规则，并且知道"零人工 / 零漏发 / 零 CAPEX 三者只能取二"。

### (3) Rule 1 数据不可变 —— 要主动说，不要等人查

已验证 45 个 CSV、240,635 行零改动。这是规则第一条，但项目从未在 PPT 里声明。建议原句：

> "Zero bytes of the 45 official CSV files were modified. Every number we show can be recomputed from your data."

### (4) 离线自足 —— 已合规

已核实 `src/` 与 `app.py` 无任何外部 HTTP 调用（仅注释里出现 URL 字样）。符合 Rule 的 "Zero external cloud API dependencies"。现场演示不依赖网络，但**仍要准备录屏**，因为浏览器/本机环境可能出问题。

## 9.2 漏掉的黄金数据：`network_kpis.csv`

这是整个补充里价值最高的一条。此前所有分析都只用 `baseline_kpis.csv`（5 个精查站），但 `network_kpis.csv` 有 **95 个网络级站点**，字段直接对应能量维度的四个评分对象：

| 实测汇总（95 站） | 数值 |
|---|---|
| 总能量 | 13,368.6 MWh |
| **需求超电网限值总时长** | **2,096.1 小时** |
| **超限站点数** | **72 站** |
| **峰值功率恰好等于电网限值的站点数** | **72 站** |
| 欠电发车总数 | 352 |
| 公共充电放弃 | 26,482 / 169,006 = **15.67%** |
| 可用率均值 | 99.56% |

### 为什么这条数据是决定性的

**72 个站的 `peak_grid_kw` 与 `grid_limit_kw` 分毫不差（例如 SE-24 都是 2050，FI-13 都是 1250）。** 自然负荷不可能刚好等于限值——这是**有人实时压功率的指纹**。

于是能量维度的 "grid limits" 那一项有了一个无法反驳的答案：

> "在 95 个站点里，有 72 个站的峰值功率恰好停在电网限值上，累计 2,096 小时需求超过限值。这意味着今天有人在实时压功率——每一次都是一次人工操作。我们的方案把这 2,096 小时变成算法自动完成。"

这句话同时做到三件事：
1. 用官方字段回答 "grid limits"（20% 权重）
2. 把"削峰"翻译成"人工工时"，与 20.76 FTE 的主线合并
3. **顺手修掉"0 越限"的循环论证**——真正的答案不是"我们 0 越限"，而是"基线本来就靠人压着才没越限"

### 两个口径陷阱

- **站点基数**：`sites.csv` 5 站（S1–S5 精查）+ `network_kpis.csv` 95 站 = 100 站。PPT 里说"100 站"时**必须**注明这个拆分，否则被问"为什么两份数据站数不同"会很难看。
- **不可混算**：`network_kpis.csv` 不含 S1–S5，所以 2,096 小时不能和 S1 的场景日数字相加或对比。
